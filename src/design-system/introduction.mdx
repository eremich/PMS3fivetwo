## How the tokens are organised

Three tiers. Components only ever touch tiers 2 and 3, so a theme change or a rebrand is an edit in one file.

<Tiers />

Names follow `--category-purpose-state`, with the state always last (`--action-primary-hover`). In markup the
category word is dropped because Tailwind already adds it: `bg-primary-hover`, `text-fg-secondary`, `border-line`.

## Principles

- **Tokens first.** No raw colours, radii or font sizes in components; if a value is missing, add a token.
- **One definition per state.** Hover, focus, pressed and disabled are defined once and reused everywhere.
- **Themes are data.** Components never branch on light or dark; the semantic tokens resolve per theme.
- **Accessible by default.** AA contrast in both themes, visible keyboard focus, labels wired to controls.
- **Hover means clickable.** Non-interactive rows and cards have no hover.

## Working with the system

1. Need a colour or state? Add or extend a token in `src/styles/tokens/`, then bridge it in `theme.css`.
2. Build the component from tokens only, and write its story with every variant and state.
3. Document it: what it is, when to use it, do and don't, accessibility notes.
4. Run `python scripts/check-tokens.py` before committing.
